# Core access, auth, route integration

## Can a public visitor create or take over a privileged account?

### Takeaway
Yes. Code inspection confirms two independent critical paths: crafted public registration accepts `id_role=1` (Administrator), and the public password reset flow lets anyone who knows a username obtain the reset form and change that account's password without proving control of its email.

### Cited Findings
- **Critical — public self-registration can assign Administrator.** GET and POST `/register` are public; POST invokes `RegisterController::create`. `UserRequest` checks only that `id_role` exists and that `id_branch` names an existing branch, while `create` persists the submitted role ID to `role_user`. Role 1 is seeded as `Administrator`; `RoleMenu::checkAccess()` unconditionally allows role 1. Reproduction reasoning: fetch CSRF token, submit valid `full_name`, new `email`, `password`, `id_role=1`, and any valid `id_branch[]`; then log in as the new account. The HTML registration form does not offer these fields, so an ordinary form submission is rejected by validation, but an HTTP client can submit them. — [public route](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/web.php:19), [request validation](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Requests/UserRequest.php:24), [role assignment](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/Auth/RegisterController.php:29), [Administrator seed](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/database/migrations/2024_10_16_093137_create_role_table.php:25), [role 1 bypass](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Models/RoleMenu.php:25), [form omissions](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/resources/views/auth/register.blade.php:73).
- **Critical — public reset does not establish account ownership.** Public POST `/forgot-password` finds a user by supplied username and renders a page containing `encrypt($user->id_user)`; public PUT `/forgot-password` calls `decrypt($request->id_user)` and immediately changes that user's password. No mail delivery, one-time token, expiry, or other ownership check appears in this route/controller path. Reproduction reasoning: POST a target's known email/username with a CSRF token, extract the returned hidden `id_user`, PUT it with a new valid password, then authenticate as the target. The encryption only protects the numeric ID from tampering; the server hands the ciphertext to the requester. — [routes](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/web.php:16), [username lookup](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/DashboardController.php:136), [reset write](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/DashboardController.php:154), [hidden ID](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/resources/views/forgot-password.blade.php:73).
- **High — all roles are granted every configured permission on fresh migration.** The `role_menu` migration iterates every row in `role` and every configured action, then bulk-inserts every pair. Thus newly migrated standard roles initially have the same permission set as Administrator until explicitly restricted. — [migration](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/database/migrations/2024_10_16_093148_create_role_menu_table.php:46), [permission gate](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Models/RoleMenu.php:25).

### Inferences
- Disable the public register and custom reset routes until fixed. Rebuild reset with Laravel's broker and emailed expiring token; create users/assign roles only through an authenticated authorized flow. Seed least privilege role permissions rather than the full Cartesian product.

### Gaps
- No live exploit attempt or database write was performed. Actual production records and deployment exposure were not checked.

## Does authorization track the current authenticated user and branch?

### Takeaway
No. The permission and branch gates trust the `role` value saved in session at login; impersonation changes the authenticated user without refreshing that session value. Role assignment edits can also leave an existing session with its previous powers.

### Cited Findings
- **High — impersonation retains the administrator's permission and branch scope.** Login saves the initial user's role into `Session('role')`. The impersonation action permits user ID 1, calls `Auth::login($target)`, and does not replace or clear that session role. `RoleMenu::checkAccess()` then still grants all actions when the session role is 1, and `UserBranch::getUserBranch()` returns all branches under the same condition. Reproduction reasoning: sign in as seeded admin user 1, call `/user/impersonate/{non_admin_id}`, then visit a route protected by `requireAccess` or query a branch-scoped dashboard; Auth identifies the target but authorization still follows the old admin role. — [login session write](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/Auth/LoginController.php:46), [impersonate](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/UserController.php:207), [role permission check](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Models/RoleMenu.php:25), [branch scope](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/Modules/Master/Entities/UserBranch.php:24).
- **High — changing a user's assigned role does not revoke the old session role.** `UserController::update()` deletes and reinserts `role_user`, but authorization never re-reads that assignment: `RoleMenu::checkAccess()` uses only `Session('role')['id_role']`. A downgraded user with an existing session continues to get checks under the former role until a new login. — [role update](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/UserController.php:125), [session gate](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Models/RoleMenu.php:25).
- **Medium — role middleware is not applied to most routes.** The kernel registers `role` middleware, but module route groups and core admin routes use only `auth`; individual controller methods provide the authorization checks. For example, `GET /user/data` and `GET /roles/data` have no `requireAccess`, so any authenticated account can retrieve full user (names, username, email, branches and role) or role datasets by direct request even when the corresponding index page is denied. — [middleware alias](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Kernel.php:68), [admin routes](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/admin.php:31), [user data](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/UserController.php:219), [role data](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/P_role.php:275).
- **Medium — user DataTable inserts unescaped user names into raw HTML.** `nm_user` returns `$row->nm_user` and `$row->username` directly, and `rawColumns()` exempts the column from DataTables escaping. Those fields can be set through registration or user editing. A stored HTML/JS value can run when an administrator loads this table, depending on client DataTables rendering. — [HTML construction](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/UserController.php:243), [raw column](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/UserController.php:278), [public value source](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/Auth/RegisterController.php:35).

### Inferences
- Resolve role and allowed branches from the authenticated user's current database assignment for sensitive actions, or invalidate affected sessions on role changes. Impersonation should establish the target's role and regenerate session state. Protect each data endpoint with the matching permission; HTML-escape every user field before enabling raw table output.

### Gaps
- No live session was switched and no production role assignments were read. The XSS exploitability depends on the client DataTables setup, although the server returns unescaped HTML.

## Do core routes and controller methods match expected behavior?

### Takeaway
Most audited routes boot and resolve, but several core behaviors are broken or ambiguous: the normal registration form omits mandatory fields, one resource action has an unresolvable request class, and route names are duplicated.

### Cited Findings
- **Medium — normal registration cannot pass its own validation.** The public form supplies `full_name`, `email`, `password`, `captcha`, but `UserRequest` requires `id_role` and an `id_branch` array. The controller's fallback role 99 is unreachable for requests validated by `UserRequest`. — [form](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/resources/views/auth/register.blade.php:73), [validation](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Requests/UserRequest.php:24), [controller](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/Auth/RegisterController.php:29).
- **Medium — `POST /role-menu` cannot resolve its FormRequest.** `P_rolemenu::store(UserRequest $request)` refers to an unqualified `UserRequest` in namespace `App\Http\Controllers`; the file imports `RoleMenuRequest` but not `UserRequest`. It also references `Hash` and `RoleUser` without imports after entering the method. — [controller imports](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/P_rolemenu.php:3), [store method](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/app/Http/Controllers/P_rolemenu.php:47), [resource route](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/admin.php:26).
- **Low — duplicate route names make URL generation ambiguous.** Read-only `php artisan route:list --json` inspection found duplicate names for `crm.dashboard` (`/crm-dashboard`, `/dashboard`), `forgot-password` (GET/POST/PUT), and several module operations (`pos.receipt`, `product-stock-data`, `receipt.delete-ajax`, `production.edit-ajax`, `production.get-receipt`, `receipt.edit-ajax`, `wholesale.receive_product`). — [dashboard routes](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/admin.php:16), [CRM route](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/Modules/Crm/Routes/web.php:35), [forgot routes](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/web.php:16), [transaction routes](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/Modules/Transaction/Routes/web.php:25).
- **Verification performed:** `php artisan route:list --path=forgot-password`, `--path=change-password`, `--path=roles`, `--path=user`, and `route:list --json` completed and confirmed action/middleware mappings. `php -l` passed for the six inspected core PHP files. These checks do not execute controller logic or prove database behavior. — [route definitions](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/web.php:16), [admin definitions](/Users/maaullntechicloud.com/Develop/sheetup-projects/infruity-main/routes/admin.php:16).

### Inferences
- The broken role-menu store action appears to be legacy code; decide whether to remove its route or implement it using a request/model matching the current permission schema. Give distinct route names to different operations, then inspect generated URLs used by views.

### Gaps
- No HTTP requests with database writes were made, and no migrations or app tests were run. Production route cache, production config, and external reverse-proxy controls were not inspected.
